# 开发约束与编码指南

## 1. 核心业务规则

开发时必须遵守以下规则：

1. 学生端只能使用已审核并发布的题目。
2. AI 输出必须进入人工审核，不得直接发布。
3. 答错后必须提供错后学习导航。
4. 奖励机制奖励成长行为，不鼓励刷简单题。
5. API Key 只能保存在后端加密配置中，不能进入前端。
6. 学生端不得展示“乱做”“低投入”等负面标签。
7. 每道正式题目必须有审核状态。
8. 每道正式题目应挂接至少一个知识点。
9. 知识图谱关系应支持前置依赖，不得只依赖父子关系。
10. 修改核心流程时必须同步更新 docs 文档。
11. 排行榜必须围绕成长行为设计，不得只按刷题数量排名。

## 2. 新功能开发前检查

实现新功能前，先确认：

- 是否符合 PRD.md 的产品定位。
- 是否影响学生诊断学习闭环。
- 是否涉及 AI 结果发布。
- 是否涉及权限和数据隔离。
- 是否需要新增数据字段。
- 是否需要新增审核状态。
- 是否需要新增测试或验收标准。

## 3. 学生端反馈规则

允许：

- “这题提交得有点快，建议先抓关键词。”
- “这题可能卡在前置概念，我们先补基础。”
- “你花了时间思考，这种推理过程很重要。”

禁止：

- “你在乱做。”
- “你不认真。”
- “低投入作答。”
- “你太粗心了。”

内部系统或老师端可以显示行为信号，但学生端必须使用温和、可行动的表达。

## 4. 奖励机制规则

奖励重点：

- 连续学习。
- 补清前置知识。
- 认真思考。
- 错题复盘。
- 核心素养进步。
- 从“难”到“会”的突破。

避免：

- 大量奖励简单答对。
- 引导学生刷低难度题。
- 答错后简单惩罚，导致学生害怕挑战。
- 排行榜只看答题数量或总答对数。

## 5. AI 开发规则

- AI 调用必须在后端执行。
- AI 输出必须结构化。
- AI 输出必须可追踪到任务 ID。
- AI 结果进入审核队列。
- 人工审核结果优先级高于 AI 结果。
- 模型失败时应记录原因，并按配置重试或切备用模型。

## 6. 数据安全规则

- 密码必须哈希存储。
- API Key 必须加密存储。
- 学生数据必须按权限隔离。
- 老师只能查看授权班级。
- 日志不得写入敏感明文。

## 7. 代码组织建议

后续正式工程建议按模块组织：

```text
src/
  modules/
    auth/
    users/
    knowledge-graph/
    questions/
    exams/
    ai/
    review/
    learning/
    rewards/
    reports/
```

模块之间通过明确服务接口协作，避免在前端或控制器里堆业务逻辑。

## 8. 验收标准写法

每个功能应有验收标准。

示例：

功能：错后学习导航

- 学生答错后能看到错因提示。
- 系统能推荐前置知识点。
- 学生可以进入前置知识点补救。
- 补救完成后回到原知识点复测。
- 学生端没有负面行为标签。
- 答题记录保存是否触发补救。

## 9. 文档同步要求

以下情况必须更新文档：

- 新增模块。
- 新增核心数据字段。
- 修改审核流程。
- 修改 AI 任务输入输出。
- 修改奖励规则。
- 修改知识图谱关系规则。
- 修改学生端反馈策略。
